Vibes vs. Evidence: What actually delivers AI code review quality

By Dave Sifry (GitHub · LinkedIn). This is the short version for working developers. Researchers and sceptics: every number here comes from the full report, which has the method, the intervals, the caveats and a reproduction chain.

Everyone has an opinion about AI code review: which model to buy, whether an agent harness is worth the tokens, and how much “thinking” to pay for. We stopped guessing and measured it. Here is what you can use this week.

The short answer

Run a harness, on an open-weight model, at low effort

  • Use a harness, not a single prompt. The same model found {{hv_ratio}}× the verified bugs running a harness, and the harness won {{hv_pos}} of {{hv_pairs}} like-for-like comparisons. The top {{harness_lead}} of {{n_cells}} configurations are all harness runs.
  • Open-weight models have reached parity on AI code review, at a fraction of the price. {{pilot_model_full}} running metareview matched {{closed_model_full}} running the same harness ({{pilot_score}} against {{closed_score}}) at {{pilot_vs_closed}} the cost. All {{n_open_h}} open-weight harness configurations outscored every closed-model one-shot prompt, and only {{n_closed_above}} of the {{n_closed_h}} closed-model harness configurations scored higher.
  • Low or medium effort is enough. High effort showed no measurable gain over medium in {{eff_unresolved}} of {{eff_pairs}} head-to-heads, and it cost more in {{eff_cost_more}} of them.

Finding · harness

A harness finds more real bugs than a single prompt

“One-shot” means pasting the diff into a single, carefully engineered prompt (read the exact prompt → REPORT §2.2). A harness makes the same model work the review in passes, with tools and specialised reviewers. We tested the open-source harnesses Compound Engineering (“CE” in the charts) and metareview (“MRV”). Holding the model and effort level fixed, the harness found more verified bugs in {{hv_pos}} of {{hv_pairs}} comparisons, a mean gain of {{hv_recall_pts}} points of recall.

What it costs you. A harness spent a median of {{tok_mult}}× the tokens, about {{cost_mult}}× the dollars and {{wall_mult}}× the wall-clock time of the same model run one-shot. At low effort the median harness review took {{wall_harness_low}}, against {{wall_oneshot_low}} for one-shot. It also says more: the median harness configuration produced {{unsup_harness}} unsupported findings (“hallucinations”) across the {{n_prs}} reviews against {{unsup_oneshot}} for one-shot, alongside {{advice_harness}} accepted useful suggestions against {{advice_oneshot}}. More signal, but more to triage.

The score is built from the bug, suggestion and unsupported columns. Verified bugs count most. A useful suggestion (an “accepted advisory” in the full report) is a finding that is true and worth a maintainer’s attention but is not a correctness bug or a style nit; it earns credit. An unsupported finding is a false claim, a style-only comment or vague speculation; it costs points. Bugs are proven by tests. Suggestions and unsupported findings are judged by a model, and a finding the judge was unsure about counts as neither. How the score works → REPORT §2.6

Finding · effort

More thinking mostly bought a bigger bill

We compared high against medium reasoning effort for the same model and way of working, on the same pull requests. When the interval crosses zero, this sample cannot tell them apart. That happened in {{eff_unresolved}} of {{eff_pairs}} comparisons, while high effort cost {{eff_cost_lo}}× to {{eff_cost_hi}}× as much.

How to read the bars. Each bar is a confidence interval: the range the true effect plausibly falls in, given how much the result moved from one pull request to the next. A high dot with a wide bar is not a win. {{eff_ex_label}} shows a gain of {{eff_ex_d}}, but its interval runs from {{eff_ex_lo}} to {{eff_ex_hi}}, so high effort may have helped, done nothing, or hurt. Each configuration ran once, so run-to-run variation is not in these bars; the real uncertainty is, if anything, wider.

The cost was reliable. The benefit was not. High effort cost more in {{eff_cost_more}} of {{eff_pairs}} comparisons and found measurably more in {{eff_better}}. The clearest gain was {{eff_best_label}} ({{eff_best_d}}, interval {{eff_best_lo}} to {{eff_best_hi}}), and even there a harness was the better buy: {{eff_best_model}} running either harness at low effort found more verified bugs ({{eff_best_ce_low_bugs}} and {{eff_best_mrv_low_bugs}}) than {{eff_best_model}} one-shot at high effort ({{eff_best_high_bugs}}).

Effort did not add noise. High versus low was not formally tested, but on raw counts high effort found a mean of {{eff_lohi_more_bugs}} more bugs out of {{gold_total}} than low, and unsupported findings went down in {{eff_unsup_down}} of {{eff_lohi_pairs}} configurations and up in {{eff_unsup_up}}.

This needs more research. More pull requests and repeated runs could resolve effects this sample cannot. For now the effects are not large enough to justify recommending anything beyond this: use a harness, at low or medium effort. Open questions → REPORT §6

How we kept score

We only counted bugs we could prove

The public benchmark’s human reviewers labelled {{gold_benchmark}} bugs in these pull requests. The models kept reporting more. So we audited them: every one of the {{gold_hidden}} additional bugs has a test that fails on the pull request and passes on the fix. That gives {{gold_total}} verified bugs to score against.

Why {{n_prs}} pull requests, when the campaign ran {{n_bench_prs}}? The full campaign made {{n_runs}} healthy review runs over all {{n_bench_prs}} benchmark pull requests in {{n_bench_codebases}} codebases. Proving every bug with a test is expensive, so we ran the complete grid, every model running every harness at every effort level, on the {{n_prs}} highest-severity pull requests, picked by a criterion fixed in advance. That is the like-for-like set every comparison here uses.

Then we checked the slice against the rest, using the benchmark’s own labels across the {{sel_cells}} configurations that also ran all {{n_bench_prs}} pull requests.

What held up: each configuration found about the same share of the labelled bugs on the {{n_prs}} as on all {{n_bench_prs}} (a mean gap of {{sel_recall_gap}}), and the order of the models held or nearly held in {{rank_high}} of {{rank_groups}} groupings.

What did not: harnesses looked better on the {{n_prs}} than they do across the whole benchmark. On the other, lower-severity pull requests they raised more unsupported findings, which pulled their overall quality score (F1, which balances bugs caught against false alarms) down by about {{sel_f1_gap_abs}} on a zero-to-one scale. {{pilot_model_full}} running metareview at {{pilot_effort}} effort, for example, scored {{pilot_f1_six}} on the {{n_prs}} and {{pilot_f1_full}} on all {{n_bench_prs}}.

So read this page for which setup beats which, not for the exact scores, and expect a harness to be somewhat noisier on lower-severity pull requests than these numbers suggest. The full check → REPORT §2.4.2

What to do with this

Next steps for you and your team

  1. Run a harness, not a single prompt.If your AI review is a single prompt over the diff, this is the biggest lever we measured: more verified bugs in {{hv_pos}} of {{hv_pairs}} like-for-like comparisons.
  2. Pilot an open-weight model at low effort.Both harnesses are open source and free, so try each on your own pull requests. Running metareview, {{pilot_model_full}} at {{pilot_effort}} effort found {{pilot_bugs}} bugs at {{pilot_cost}} and about {{pilot_secs}} seconds a review; {{cheap_model_full}} is the budget option at {{cheap_cost}} ({{cheap_bugs}} bugs), with more unsupported findings to triage ({{cheap_unsup}} against {{pilot_unsup}}). Running Compound Engineering, {{ce_pilot_model_full}} at {{ce_pilot_effort}} effort was the cheapest and fastest harness configuration we measured: {{ce_pilot_bugs}} bugs at {{ce_pilot_cost}} in {{ce_pilot_dur}}, with {{ce_pilot_unsup}} unsupported findings. Compound Engineering also holds the top score overall ({{top_model_full}} at {{top_effort}} effort: {{best_bugs}} bugs at {{top_cost}} a review).
  3. Vet the provider before you send it your code.Open weights mean many hosts can serve the same model, and their terms differ widely. Look for inference that stays inside your legal jurisdiction; no data retention, with prompts and outputs never written to disk; a contractual commitment not to train on your data; and terms that let you use the output however you want, including commercially. Read the model’s own licence for commercial use as well. If no host meets that bar, open weights leave you the option of running the model yourself. We did not audit any provider’s data practices, so get these in writing.
  4. Default to low or medium effort.Make high effort earn its place on your own pull requests before you pay for it everywhere.
  5. Measure triage time yourself.We measured bugs found, noise, dollars and seconds. We did not measure developer time saved, and that is the number that decides whether any of this is worth it for your team.

What this does not prove

  • The headline numbers come from {{n_prs}} pull requests. They are the highest-severity ones in a {{n_bench_prs}}-PR benchmark, from {{n_codebases}} of its {{n_bench_codebases}} codebases. The check against the full benchmark covers recall and rankings on the benchmark’s own labels; the {{gold_total}} verified bugs exist only for these {{n_prs}}. This is evidence for running a pilot, not proof about your repository. §2.4
  • A single run per configuration. The intervals cover which pull requests were sampled, not run-to-run variation in the models. §4
  • Models did much of the judging. Verified bugs rest on executed tests, but “useful advice” and “unsupported” are model judgments, not human ones, and a GLM-family judge may favour GLM output. §2.6
  • Some runs have known gaps. The GLM harness runs predate a gateway fix, and Fable’s harness grid was not completed for budget, so Fable is excluded from the harness comparisons. §2.3.4
  • Costs are list prices (retrieved {{price_date}}), not invoices, and exclude failed gateway calls. §3.4.1
  • The author wrote one of the harnesses. See the disclosure at the top. §2.3.5
